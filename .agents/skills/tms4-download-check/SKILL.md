# TMS4 다운로드 자료 점검

배경, 기록지 구조, 판단 사례는 references/research.md를 따른다.

## 규칙
- 원자료 값은 바꾸지 않는다. 판단은 flag 열로, 복원값은 vwc_qc 열로 남긴다.
- 다음이 없으면 추정하지 말고 먼저 묻는다: 현장 기록지, 기록지 시각과 UTC의 차이, 센서-지점 대응표.
- 애매한 하강은 플래그를 정하지 말고 0으로 둔 채 '확인 필요'로 보고한다.

## 플래그 (겹치면 9 > 1 > 8 > 4 > 3 > 0)
- 0 정상, 9 결측(NaN, 설치 전·땅 밖·0값, VWC 60% 초과), 8 한 기록만 튀는 스파이크(앞뒤 1%p 이상)
- 1 TMS 자료를 내려받은 방문의 도착~출발 시각 (다운로드 없는 방문은 제외)
- 3 외력 접촉으로 떨어졌다가 기록지상 복구 후 급회복한 구간 (복원값 사용)
- 4 외력 접촉으로 떨어진 뒤 회복이 없는 구간 (파일 끝까지)

## 절차
1. 기록지를 읽는다. site_list에서 센서-지점-설치 시각을 정리하고, 같은 센서가 두 지점에 있으면 이설로 본다. site_record에서는 TMS, mushroom, S##, L##이 들어간 항목만 읽어 다운로드 방문, 훼손(pee, 동물, 뚜껑), 복구(흙 채움, 재설치), 이설·철거를 정리한다. 모든 시각은 UTC로 바꾼다.
2. CSV를 읽는다(세미콜론, 열: 순번, 시각(UTC), T1, T2, T3, 원시값, VWC(%), 오류). 이전 다운로드와 겹치면 시각 기준으로 중복을 지우고 최신 파일을 남긴다. 15분 간격, 결측 행, 오류 플래그를 확인한다.
3. 설치 시각은 VWC가 0에서 처음 양수가 된 기록으로 정한다. 설치 전 기록은 출력에서 빼고, 설치 후 0값은 9로 둔다.
4. 15분 사이 VWC가 0.5%p 이상 떨어진 기록을 찾는다. 기록지의 강수와 방문 시각에 대조한다. 같은 센서에 이후 복구 기록과 급상승이 있으면 하강 시점부터 회복 직전까지 3으로 두고 복원한다. 복원은 구간 양끝을 잇는 직선을 뺀 anomaly에 (하강 직전값~회복 직후값 직선)을 더한다. 복구 기록이 없으면 4로 둔다.
5. 이설 전후는 지점별 파일로 나눈다. 파일 이름은 지점_센서_시작_끝(UTC, YYYYMMDDHHMM).csv, 열은 time_utc, time_local, T1, T2, T3, raw, vwc_raw, vwc_qc, flag.

## 워크플로
단계는 이 순서로만 진행한다. 단계마다 중간 결과를 `<출력 폴더>/_work/`에 파일로 꺼내 놓고, 관문을 통과해야 다음 단계로 간다. 관문에 걸리면 그 단계에서 멈추고 이유를 말한다.

| 단계 | 할 일 (절차 번호) | 꺼내 놓을 중간 결과 | 관문 |
|---|---|---|---|
| 1 | 입력 확인 | `_work/01_inputs.md`: CSV 목록(센서·다운로드 날짜), 기간(UTC·현지), 기록지 파일, 시각 차이 | 기록지·시각 차이·센서-지점 대응표가 모두 있다. 하나라도 없으면 묻는다 |
| 2 | 기록지 정리 (절차 1) | `_work/02_field_events.csv`: site, sensor, event(download/damage/repair/move/remove), time_local, time_utc, note | 모든 시각이 UTC로 바뀌었고, 사건마다 센서가 정해졌다. 센서를 못 정한 사건은 `unclear`로 남긴다 |
| 3 | 다운로드 상태 (절차 2) | `_work/03_download_status.csv`: 파일별 행 수, 겹친 행, 빠진 행, 오류 플래그 | 겹침을 지운 뒤 같은 시각이 두 번 나오지 않는다 |
| 4 | 설치 구간·이설 (절차 3, 5) | `_work/04_deploy.csv`: sensor, site, start_utc, end_utc, 근거 | 센서마다 구간이 겹치지 않는다. 입력에 있는 센서가 전부 들어 있다 |
| 5 | 하강 후보 (절차 4) | `_work/05_drops.csv`: sensor, time_utc, dv, 기록지 근거, 판단(3/4/확인 필요) | 후보마다 근거 행이나 '확인 필요'가 붙어 있다 |
| 6 | 계획 확인 | 아래 '계획'의 표 | 사용자가 확인했다 |
| 7 | 플래그·복원 실행 | `scripts/tms4_flag.py`의 DEPLOY·VISITS·CONTACT 갱신, `<출력 폴더>/*.csv`, `processing_log.txt` | 스크립트가 오류 없이 끝났다 |
| 8 | 검증 | `<출력 폴더>/check_report.txt` | `check_result.py`가 ERROR 0 (아래 '검증') |
| 9 | 보고 | '출력 형식' 여섯 항목 | WARN과 REVIEW가 모두 '확인 필요'에 들어 있다 |

1~5단계는 읽기만 한다. 원자료 폴더와 기록지는 열어 보기만 하고, 쓰는 것은 `_work/`와 출력 폴더뿐이다.

## 계획
6단계에서, 스크립트 설정을 고치거나 출력 파일을 쓰기 전에 아래를 한 번에 보여 주고 확인을 받는다. 확인 전에는 7단계로 가지 않는다.

- 입력: 파일 수, 센서 수, 기간(UTC와 현지시각)
- 바꿀 설정: DEPLOY·VISITS·CONTACT에 더하거나 고칠 행 (바뀌는 것만, 표로)
- 판단 예정: 3·4로 둘 구간(센서, 시작~끝, 근거), '확인 필요'로 둘 구간
- 만들 파일: 출력 폴더와 파일 이름 목록
- 묻는 것: 관문에서 걸린 것(대응표에 없는 센서, 기록지에 없는 사건 등)

사용자가 일부만 고치라고 하면 그 부분만 반영해 계획을 다시 보여 준다. 사용자가 자리에 없으면 1~5단계 결과와 계획까지만 남기고 멈춘다.

## 검증
끝내기 전에 반드시 돌린다.

```
python .agents/skills/tms4-download-check/scripts/check_result.py <TMS CSV 폴더> <출력 폴더>
```

- 결과는 화면과 `<출력 폴더>/check_report.txt`에 남는다. 종료 코드 1이면 ERROR가 있다.
- ERROR(E1~E15)는 규칙 위반이다. 원인을 찾아 설정이나 스크립트를 고치고 7단계부터 다시 돌린 뒤 다시 검증한다.
- 고쳐서 다시 돌리는 것은 2번까지다. 두 번 고쳐도 ERROR가 남으면, 또는 고치려면 값을 짐작해야 하면(대응표에 없는 센서 E13, 규칙에 없는 값 등) 더 고치지 말고 멈춰서 ERROR 줄과 고칠 방법 후보를 보여 주고 묻는다.
- WARN(W1~W5)은 고칠 대상이 아니라 보고 대상이다. 줄마다 '확인 필요'에 옮긴다.
- 검증을 통과하지 않은 결과는 '완료'라고 보고하지 않는다. 보고 첫 줄에 `check_result.py: PASS` 또는 `FAIL (ERROR n)`을 적는다.

## 훅·권한
하지 말 것
- 원자료(TMS CSV, 현장 기록지 xlsx)를 고치거나, 옮기거나, 지우지 않는다. 열어 보기만 한다.
- 기록지에 없는 시각·사건, 대응표에 없는 센서-지점, 복구 시각을 짐작해 채우지 않는다. 비워 두고 묻는다.
- 검증을 건너뛰거나, ERROR를 없애려고 check_result.py의 기준을 바꾸지 않는다.

훅으로 막을 것: 저장소의 `.claude/settings.json` 예 (원자료는 `data/raw/` 아래에 둔다고 가정)

```json
{
  "permissions": {
    "deny": [
      "Edit(data/raw/**)",
      "Write(data/raw/**)",
      "Bash(rm:*)",
      "Edit(.agents/skills/tms4-download-check/scripts/check_result.py)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit|NotebookEdit|Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 .agents/skills/tms4-download-check/scripts/guard_raw.py"
          }
        ]
      }
    ]
  }
}
```

`scripts/guard_raw.py`는 도구 호출을 받아, 원자료 폴더(`TMS4_RAW_DIR`, 기본 `data/raw`)나 원자료 이름(`지점_센서_YYYYMMDD.csv`, `*.xlsx`)을 쓰거나 지우는 호출이면 종료 코드 2로 막고 이유를 돌려준다. 권한 규칙은 경로 이름으로, 훅은 내용(파일 이름 형식, `rm`·`mv`·`sed -i`·`>` 같은 명령)으로 막아 서로 빈틈을 메운다.

## 서브에이전트
센서가 10개 이상이거나 지점이 여러 곳일 때만 나눈다. 그보다 작으면 혼자 한다. 설정 고치기(7단계), 판단 확정, 보고는 나누지 않고 주 에이전트가 한다.

| 조각 | 목표 | 결과 모양 | 도구 | 경계 |
|---|---|---|---|---|
| 기록지 일꾼 (2단계, 1명) | 기록지에서 TMS·mushroom·S##·L## 항목을 사건표로 | `_work/02_field_events.csv` (워크플로의 열) | Read, Bash(python으로 xlsx 읽기) | 기록지는 읽기만. `_work/02_*`만 쓴다. 시각을 못 읽으면 `unclear` |
| 하강 후보 일꾼 (5단계, 지점마다 1명) | 맡은 지점 센서에서 0.5%p 이상 하강을 찾아 사건표와 맞춘다 | `_work/05_drops_<지점>.csv` | Read, Bash(python, 읽기 전용) | 플래그를 확정하지 않는다(판단 후보만). 스크립트·원자료를 고치지 않는다. 맡은 지점 밖은 보지 않는다 |
| 검토 일꾼 (8단계, 1명, 작업을 보지 않은 새 일꾼) | 출력이 규칙을 지키는지 따로 확인 | `check_report.txt` + 보고 초안과 어긋나는 점 목록 | Bash(`check_result.py`만), Read | 아무것도 고치지 않는다. 주 에이전트의 설명이 아니라 파일과 SKILL.md만 근거로 삼는다 |

일꾼에게는 이 SKILL.md, 맡은 입력 경로, 결과 파일 이름만 넘긴다. 주 에이전트는 일꾼 결과를 합친 뒤 워크플로 관문을 직접 확인한다.

## 출력 형식 (이 순서로)
0. 검증 결과: `check_result.py: PASS` 또는 `FAIL (ERROR n)`, WARN 수
1. 입력 정보: 파일 수, 기간(UTC와 현지시각), 기록지 시각 차이
2. 다운로드 상태: 파일별 간격·중복·결측·오류 플래그
3. 센서별 설치 구간과 이설 내역
4. 파일별 플래그 개수
5. 3·4 구간 목록: 시작, 끝, 근거 기록, 보정량
6. 확인 필요 구간과 이유 (REVIEW, WARN 포함)
